# 提示词契约

## 可裁剪结构

以下是构件，不是必须全部出现的长模板。简单任务保留目标、输入、约束和输出即可。

```text
任务：为【对象】完成【动作】，帮助【使用者】做出【决定/产物】。
输入：材料位于【变量/附件】，可信业务规则为【规则来源】。
成功标准：【可观察的结果】。
处理方式：先检查必要输入；完成【必要步骤】；用【验收方式】检查结果。
约束：【不得改变的业务事实、范围、预算或格式】。
缺失信息：决定性缺口提出具体问题；其余标明“假设/未知”并完成可做部分。
输出：【结构、字段、语言、长度或文件格式】。
完成条件：【使用者能直接检查的条件】。
```

对 Agent 再补充：真实可用工具与调用条件、工具失败的恢复方式、外部动作的授权边界、需要用户决策时的停止点。没有工具时给出可执行方案，不伪造调用结果。

## 稳定规则与配置

| 稳定规则 | 场景配置 |
|---|---|
| 事实必须可追溯 | 本次资料位置、参考日期 |
| 缺失数据不能编造 | 产品名、目标读者、报告周期 |
| 输出遵守契约 | Markdown / JSON / 文档结构 |
| 实际动作要有执行证据 | 当前可用工具及项目路径 |

不要把个人姓名、某台电脑路径、某个模型版本、固定提问数量写进可迁移的稳定规则。用户明确要求固定时，作为配置保留。

## 结构化输出

例：需求归类结果。

```json
{
  "requirement_id": "REQ-01",
  "category": "usability",
  "evidence_ids": ["S1"],
  "confidence": "supported",
  "open_question": null
}
```

在提示词中定义 `category` 可选值、`evidence_ids` 如何对应输入、`confidence` 的含义、空数组与 `null` 的差别。校验应检查语法、类型、枚举和语义约束，例如引用 ID 必须存在。程序解析失败时提供错误信息供修正，设置符合业务需要的重试上限；仍失败则返回清晰的失败状态，不能静默补造字段。

示例只能展示期望行为，不得夹带新的必需规则。需要多个示例时覆盖不同边界；用户资料作为数据块隔开。不要因为示例使用中文、特定人数或金额，就将它们固化成所有任务的限制。

## 冲突与变更审查

记录“原行为—问题证据—修改—保留项—验证方式”。遇到互相冲突的用户材料，指出冲突并沿用已确认的权威版本；权威性未知时只暂停受影响部分。不要自行宣布某份低层资料具有更高指令优先级。

修改顺序：先澄清目标和事实边界，再修复输出契约，再优化措辞与示例。模型/API 能力若影响方案，核对当前官方文档和实际版本，而不是复制来源中的型号或参数。
